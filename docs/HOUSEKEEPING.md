# Xcode Housekeeping

The annoying-but-correct things every iOS project should have on day 1, bottled and baked into `templates/swift/`. RN-side mirror at the bottom.

## Version management

**Single source of truth: `Seed/Version.xcconfig`.**

```
MARKETING_VERSION = 1.0.0
CURRENT_PROJECT_VERSION = 1
```

- `project.yml` references both via `$(MARKETING_VERSION)` and `$(CURRENT_PROJECT_VERSION)` for app + widget + tests, so a single bump propagates everywhere.
- `bin/bump-version <patch|minor|major>` edits the xcconfig and tags the commit. Never bump version in `project.yml` directly.

Pattern proven across multiple shipped apps before landing in the template.

## Privacy permission strings

All `NS*UsageDescription` strings live in `Localizable.xcstrings` keyed and commented out by default. Wizard uncomments only the ones for enabled features. Each string:

- Is one sentence.
- Explains *why*, not *what* the permission is for.
- Is translated for every tier-1 locale.

## Archive Command

Every App Store-bound app should expose one local archive command:

- Swift/XcodeGen: `make archive` delegates to `bin/archive-ios.sh`.
- Expo/RN: `npm run archive` delegates to `scripts/archive-ios.sh`.

The command must archive Release for `generic/platform=iOS`, write to a stable
`.xcarchive` path, and open the archive in Xcode Organizer by default. It may
run project generation and preflight checks first. App-specific prerequisites
must be explicit environment-driven hooks, for example:

```sh
ARCHIVE_PRE_CMD="../native-parser/build-ios.sh release" make archive
```

This keeps mature exceptions (say, a Rust parser that must build before the
archive) visible while preserving one muscle-memory command across the
portfolio. Signing failures
should be fixed in source-controlled project/signing settings, not hidden with
one-off local Xcode edits.

## Shared schemes

- `Seed.xcworkspace` not used (XcodeGen apps don't need one).

## Asset + l10n parity tests

`SeedTests/` ships nine "catches dumb stuff at PR time" tests. The first seven are unconditional; the last two are widget/Live Activity conditional (no-op when those targets aren't enabled):

1. **`AppIconAssetTests.swift`** — asserts `Assets.xcassets/AppIcon.appiconset` contains every required size (1024 + 60@2x/3x + 76@2x + 83.5@2x + 167 + 152, etc.).
2. **`PrivacyManifestTests.swift`** — parses `PrivacyInfo.xcprivacy`, verifies declared APIs cover code usage.
3. **`LocalizationParityTests.swift`** — every `Localizable.xcstrings` key has a translation for every tier-1 locale (or is explicitly marked `state: stale`).
4. **`WidgetLocalizationParityTests.swift`** — widget extension's *own* xcstrings has every widget-surface string. The widget-bundle-trap test.
5. **`ThemeContrastTests.swift`** — every palette pair clears AAA contrast.
6. **`HapticPatternTests.swift`** — every shipped haptic pattern loads (CoreHaptics dictionary parses).
7. **`SignatureMotionWiredTests.swift`** — the signature-motion ADR→code gate: `Theme/SignatureMotion.swift` exists AND at least one view applies `.signatureMotion()`. A motion ADR (`DECISIONS/009`) that produces no call site is a failure mode we've hit before — this fails the build instead.
8. **`WidgetEdgeToEdgeTests.swift`** *(widget-conditional)* — every widget uses `containerBackground(for: .widget)`; no `.background(...)` on the root widget view.
9. **`LiveActivityViewTests.swift`** *(Live Activity-conditional)* — all five Live Activity regions (compact leading, compact trailing, expanded, minimal, lock-screen) render with localized content across all tier-1 locales.

These fail CI before App Store rejects.

## LaunchScreen + first-frame hygiene

Modern `UILaunchScreen` JSON (no storyboard, no `LaunchScreen.storyboard` file). Locks the background color to the chosen palette's primary surface so the first frame matches the app — no flash of system white.

Wizard offers three launch styles:

- **Soft** — logo + breathing orb fade-in (warm-minimal default).
- **Instant** — immediate dark palette wash (dark-first identities).
- **Plain** — palette wash, no logo (the brutalist default).

## Localization seed

- `Localizable.xcstrings` seeded with `en` plus 6 tier-1 stubs (`es de fr pt ja zh-Hans`) — `/translate` skill fills them.
- `InfoPlist.xcstrings` for localized display name + permission strings.
- `SWIFT_EMIT_LOC_STRINGS: true` in `project.yml` so the compiler emits strings catalogs for translation.
- **Widget extension has its OWN `Widgets/Resources/Localizable.xcstrings`** (the widget-bundle trap) — strings on widget surfaces load from the extension bundle, not the host app bundle.

## Dev/Debug Premium Toggle (template pattern)

Every Swift template ships a cross-app contract for testing premium features in DEBUG **and** RELEASE builds. The pattern lets you flip premium on/off without code changes — essential for early-user testing in production where TestFlight's 90-day window doesn't cover the post-launch period.

The pattern lands in `Seed/Services/SubscriptionManager.swift` (template) and as a full recipe in `recipes/swift/dev-premium-toggle.md` (Phase 7).

### The contract

| Element | Value |
|---|---|
| Override key | `UserDefaults.standard.bool(forKey: "debug.forcePremium")` |
| Override evaluator | `SubscriptionManager.isPro` short-circuits to `true` when the key is set |
| DEBUG visibility | Toggle visible in **Settings → Developer** |
| RELEASE visibility | Hidden until **7-tap gesture on version string** in Settings → About |
| RELEASE expiry | Override auto-clears after **24 hours** of activation |
| RELEASE clear-on-update | Override cleared on every `CFBundleVersion` change |
| **Production hard-gate** | In RELEASE, `canUnlockDebugMenu` / `isForcedPremium` are **inert** unless StoreKit reports `AppTransaction.environment != .production` (cached at launch by `DebugUnlock.refreshEnvironment()`). A real App Store build can never unlock Pro through this path; fails **closed** during the launch window |
| Reviewer suppression | Likely App Store Reviewer (StoreKit sandbox/TestFlight environment + first-launch heuristic) suppresses the easter egg entirely. Uses the StoreKit 2 environment, **not** the deprecated `appStoreReceiptURL == "sandboxReceipt"` check (removed in iOS 18) |

### Why this exists

- **DEBUG side:** developing premium features needs fast iteration. Forcing real StoreKit purchases through every test cycle is impractical.
- **RELEASE side:** early-user testing of premium features after public launch. TestFlight expires (90-day cap, 10K external testers). Your own first 50 production users can validate the premium experience if they know the gesture. Apple is fine with this when the gesture is non-discoverable and the override is bounded.

### Debug menu contents (cross-app standard)

Once unlocked, the Debug menu surfaces portfolio-wide testing primitives:

- **Force Premium** (toggle, the headline feature)
- **Reset Onboarding** (button)
- **Clear All Data** (button, requires confirmation)
- **Simulate AI Unavailable** (toggle — for Foundation Models apps; verifies the nil-fallback path)
- **Simulate CloudKit Failure** (toggle — for CloudKit apps)
- **Print Analytics Stack** (button)
- **Reveal All Easter Eggs** (toggle — surfaces user-facing delights normally gated by progression)

Not all apps implement all options; the template provides the menu shell and apps wire in what's relevant.

### Apple Review safety

Apple's App Review has historically been fine with hidden dev menus when:
1. The unlock gesture is genuinely non-discoverable (7-tap is well beyond accidental)
2. The override is time-bounded (24h auto-clear)
3. The override is **inert in production** — a real App Store build (`AppTransaction.environment == .production`) can never reach Force Premium, so it can't bypass monetization at scale (the menu is for individuals in TestFlight/sandbox, never a shipped distribution channel)
4. The override doesn't compromise data security
5. Reviewer accounts are detected (StoreKit sandbox/TestFlight environment + fresh-install window) and the easter egg is suppressed for them

The recipe documents the exact heuristics + entitlement implications. See [DECISIONS/003-monetization.md](../DECISIONS/003-monetization.md) "Engineering convention" section.

### Distinction from user-facing easter eggs

The dev toggle is a **developer utility**, not a user-facing delight. The "easter eggs no user finds" forbidden category in [DELIGHT_REEL.md](DELIGHT_REEL.md) applies to *user-facing* delights — discoverable surprises meant to reward engaged users. A developer-only debug menu is a separate, allowed category. See DELIGHT_REEL.md "Forbidden delights" for the explicit clarification.

## When housekeeping breaks

If an Xcode upgrade breaks any of this, document it in [portfolio/RECENT_LEARNINGS.md](../portfolio/RECENT_LEARNINGS.md) and fix it in the template once, not in every child app.
